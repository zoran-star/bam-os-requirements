Automation Emails: Every Academy Sends As Itself

Queue item 3 · San Jose onboarding · files that change: api/_send.js + api/automations.js · email channel ONLY, SMS steps untouched

1What changes for a person

Today every automated email (lead nurture, trial confirmations, ghosted follow-ups) from ANY academy lands in the parent's inbox as "BAM Toronto <info@byanymeanstoronto.ca>". A San Jose parent who signed up with Lij's academy gets mail from a Toronto gym they have never heard of. After this build there is one hard rule: an automation email only sends when the academy's own sending domain is set and verified. Then the parent sees "BAM San Jose <info@byanymeanssanjose.com>". No domain yet? The email is HELD, nothing generic goes out in its place, and the academy owner gets a heads-up text so it is never silent. GTA parents notice nothing: their emails stay byte-identical. Automation SMS is not touched by any of this.

api/_send.jsAdd a cached resolver fromFor(clientId, vars) (mirrors resolveEmail in email-provider.js: 30s client cache, service-role fetch of clients.email_domain, business_name) plus a 5 min cached Resend GET /domains list to confirm the domain is verified. api/automations.jsEngine handles the new held result explicitly: finish({ status: "pending", run_after: now + 1h, last_error: "held: sending domain not set" }) with no attempts increment and no advance. Without this branch a held email would land in the generic skipped bucket and be silently lost, the exact trap the blank-domain empty-SMS case was criticized for. Once email_domain is set, the next hourly pass sends the held jobs in order.
api/_email.jsUNTOUCHED sendEmail already accepts from; DEFAULT_FROM is now only ever reached by legacy direct callers (commission report), never by automations.

Display name: vars.location_name (business_name via clientVars, already passed by the worker) → fetched business_name backstop. GTA byte-identity: if the computed address equals the address inside DEFAULT_FROM, return DEFAULT_FROM verbatim. That domain-match rule (no client-id hardcode) is what keeps GTA exact: GTA's business_name is "BAM GTA", not "BAM Toronto", so name-from-business_name alone would break byte-identity.

Owner notification: owner-SMS notifier (same channel as "new booking" texts), deduped to once per client per 24h via an email_events row type = "domain_hold_notice": stamp the row FIRST, then send (tz-guardrail semantics; a crash between the two can only under-notify for one cycle, never spam). Difference from the tz guardrail, stated on purpose: there the message still went out with a fallback value; here the message is held, and goes out correct later.

Edge cases
  • NULL email_domain: HOLD, never a fallback send. Job visible as pending with last_error "held: sending domain not set", owner texted once per 24h, auto-release when the domain is set. Zoran's rule: no neutral fallback, no silent send.
  • Domain set but not verified in Resend: treated the same as unset, HOLD. The cached Resend domain-list check catches it BEFORE the send, so it never burns retries on 403s and never fails as a generic error.
  • GTA byte-identical: DB-verified, GTA has email_domain = byanymeanstoronto.ca (verified in Resend), so the domain-match rule returns the exact legacy string "BAM Toronto <info@byanymeanstoronto.ca>". Zero header drift, and the hold branch is unreachable for GTA.
  • Resolver DB blip / Resend list fetch blip: HOLD for that pass (fail CLOSED, matching the new rule; the old fail-open-to-Toronto behavior is exactly the leak). The job re-checks on the next hourly pass, so a transient blip delays by at most an hour and never mis-brands. The hold notice only fires when the DOMAIN is missing/unverified, not on a transient fetch error, so owners are not pinged over a blip.
  • Shared system, no fork: everything derives from the client row at runtime. Future nicety (not this build): a clients.email_from_name runtime fact if an academy ever wants a custom display name.
