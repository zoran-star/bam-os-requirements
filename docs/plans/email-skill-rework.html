05The phases, shared by both

Run by internal BAM staff. Only the fully customizable emails reach the chat. Everything else builds without a question.

1

READ

automatic

Pull everything the academy has already entered.

  • clients.brand_data story, why_us, proof, stats, dream_athletes, voice, colours, fonts, logos
  • offer.data selling points, program structure, ages, capacity, coach ratio
  • schedule_slots sessions and venues, clients name, city, domain, phone

2

CHECK READINESS

automatic

One line per authorable email, keyed to the exact field it will be written from. Not a judgement, a fact.

  • THIN propose, and say out loud it will read thin
  • EMPTY drop the slot. Do not propose, do not invent

For each one that qualifies, the skill proposes the angle and the full copy, written out in the chat as text. No design, no rendering. Just the idea and the words, so staff can read and react fast.

The welcome email carries nothing custom any more

Its two custom lines, online programs and bring a friend, were dropped from the master on 27 Jul. With those gone the whole email builds from collected values, so it never reaches the chat. Note the consequence: GTA is the reference, so GTA stops sending those two lines as well.

4

CONFIRM OR REWRITE

staff decides

Staff confirms, edits inline, asks for a different angle, or drops the email. Nothing moves on until each one has an answer.

  • A dropped email leaves the sequence rather than shipping weak
  • Edited copy is the academy's own and never propagates anywhere else
  • The skill will not invent a fact, but staff can supply one. The guardrail is against fabrication, not against humans. If staff types a real fact the skill did not have, it uses it.
5

BUILD

automatic

Everything gets built in one pass, the photocopyable messages and the confirmed copy together. Confirmed copy drops into the shell wearing the academy's own logo, colours and fonts, assembled as blocks.

6

RENDER AND REVIEW

staff reads, notes go back to chat

The skill builds a review page in the same shape as the annotation map: a switcher across the top to flip between automations, everything for that one below.

  • Every message in send order, through the real send path. SMS as bubbles, emails as the actual HTML in a frame
  • Where every filled value came from, so a wrong source is visible and not just a wrong word
  • What did NOT render, and why. The blocks that dropped for a missing fact, listed. That is the one thing staff cannot see by reading the email
  • A short stable reference on every message and block (GH2, N1-hero, WEL-schedule) so a note points at something exactly

Staff reads, writes notes, pastes them back into the chat. The skill applies them, re-renders, and the same page updates in place.

07What has to be built that does not exist

Two things, and neither is in the codebase today. I checked the schema and the code.

A. A testimonials store

Nothing exists. No table, no column, nothing in brand_data. The one near-hit, onboarding_feedback.testimonial, is the academy OWNER reviewing BAM's onboarding, which is the opposite direction. Do not wire to it.

   testimonials
   ─────────────────────────────────────
   id            uuid
   client_id     uuid
   quote         text
   author        text        "Parent of Adam"
   source        text        'manual' | 'google'
   starred       boolean     manual ones default true
   created_at    timestamptz
  • Where: alongside "Tell your story" in the wizard, which already promises "your story and your proof". Testimonials are the missing third. Hand-typed.
  • The rule: empty means no testimonials email in either sequence. Typed means those are the ones shown.
  • Forward-compatible: when Google connects, source='google' rows join the same table and starred decides what shows. No migration later.
  • Bonus: this also feeds the free-trial page cards, which is where the Miami fabrication happened. One store fixes both surfaces.
San Jose starts empty, on purpose

GTA can be preset with its own real parents. San Jose has none, so presetting it with anything recreates the Miami problem exactly. Under the drop rule San Jose simply does not send that email until Lij supplies real ones, which is the correct outcome and better than the current state where they would send GTA's.

B. Two academy-approval steps in the wizard

The preset step's subtitle already says "Nothing texts anyone until you approve it." That approval does not exist as a step. Staff approving the render is a different gate from the academy approving the sending, and only the first one has a home today.

08Known gap, named on purpose

Nothing re-syncs when brand_data changes

The skills are one-shot. If an owner rewrites their story in the wizard next month, the built emails keep the old version silently. Handled as a support ticket when brand data changes, decided 27 Jul. Worth naming rather than leaving implicit, because it is the same drift shape this whole workstream exists to fix.

10brand_data cleanup, and what adapts to it

19 fields today. Keep 12, drop 3, move 3, one to decide. Traced against every reader in the codebase.

Ordering is not optional: backfill before you drop

GTA's website_setup.domain is EMPTY while brand_data.domain holds the domain. The field that looks like a duplicate is currently the only place GTA's domain exists. Drop it first and GTA's messages lose their website. Backfill website_setup from brand_data, point every consumer at one resolver, then drop. Doing it in that order also fixes why {{location.website}} has been falling back to the hardcoded LOCATIONS entry.

The principle

brand_data holds only what a human wrote that is recorded nowhere else. Anything countable, scheduled or configured is read live at render time. Under that rule stats disappears and the emails carry a schedule that is true on the day they send, instead of one that claimed Friday training GTA has never run.

Client websites are safe

bam-client-sites reads none of this. Checked clients/ and design-system/; the only hits were a nested worktree copy of the monorepo. Nothing dropped here can break a live academy site.

Two loose ends the trace found

The sales agent reads zero brand_data. fact-render.js and prompt-structure.js touch none of it, so the agent has no idea the academy has a story or a why-us; its selling points come only from the offer. A gap of omission, worth its own decision.

wants_about_page exists in code but not in data. api/website/team.js reads it and neither academy has it stored. A fourth category: fields the code expects that nobody ever set.
