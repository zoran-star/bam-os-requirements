Agent price breakdown

Core price, tax, and one-time fees as separate lines. Owned by the sales preset, not by any academy. PLAN 2026-07-26 blocked on PR #1587

Today the live agent says "$200 to $279 per month" and never mentions tax. A parent hears 200 and is billed 226. PR #1587 swings the other way and quotes $226 as one number. This is the third option: the agent knows all three parts and says them as separate lines. Zoran approved the wording below on 2026-07-26.

02Where each line comes from

Three numbers, three different owners. Nothing is parsed out of a string, and nothing is divided.

$315.27
Total
The catalog amount. Never derived, never recomputed. This is the money that leaves the account.

$36.27
Tax
Total minus plan. Labelled from clients.tax_config ("HST", 13).
Tax is a subtraction, not a division. 31527 - 27900 = 3627, integer cents. The three lines therefore always sum to the exact amount charged. There is no rounding risk to flag, because no rounding happens.
THE HONESTY GATE

Before printing a breakdown, the renderer re-runs the same math that built the Stripe price: applyFee(base, resolveFee({taxConfig, taxable, legacyText})). If that does not equal the catalog amount to the cent, the breakdown is not printed at all - the agent states the total and nothing else.

All three verified live 2026-07-26. A mismatch means the owner edited a base without re-pricing, or a taxable flag is wrong. Both are exactly the drift this whole workstream exists to catch (money-model risk #3 and #6), and both produce silence plus an admin flag rather than a plausible wrong line.
WHY NOT JUST DIVIDE THE TOTAL BY 1.13
  1. It assumes the fee was a percent. A flat fee, or a percent plus a flat, divides wrong and cannot be detected.
  2. It invents a number nobody typed. The owner entered 279. Division gives 278.99999999999994 and needs a round, so the "plan price" the agent quotes becomes a machine-derived figure rather than the academy's own.
  3. It can never fail. Division always produces an answer, so a mis-flagged row would silently emit a confident fake tax line. Reconciliation is the only version that can refuse.
  4. It duplicates logic. Reconciliation runs the identical _fees.js call that match-prices.js used to create the Stripe price, so the agent's breakdown and the actual charge cannot disagree by construction.
Recommendation: no schema change. Do NOT add base_cents to offer_prices. It would be a second copy of a number that already lives in the offer, and copies drift - which is the precise fault that created this workstream (a typed "13% HST" string drifting from the catalog). Offer = the owner's input. Catalog = Stripe's truth. Tax = the difference. Three things, no fourth.

Edge cases

  • Commitment base lookup. A commitment's base lives on offering.commitments[].price, matched via termFromLength(c.length). GTA's Summer Unlimited 3-month is typed as "3 Months" and resolves to 3_months. A commitment whose length does not parse yields no base, so that row falls to total-only. Correct: an unparseable length is not a number to guess with.
  • Per-row taxable precedence. A commitment's own taxable wins over the offering's, then the offering's, matching match-prices.js line for line. Any divergence here is precisely what reconciliation catches.
  • Legacy free-text rows. An academy with typed added_fees and no tax_config goes through parseFee via resolveFee, so it still reconciles and still itemizes, using the parsed label. No academy is required to migrate before it benefits.
  • Zero tax amount. If total minus base is 0, print no tax line rather than $0.00. Same for a fee of 0.
  • Negative difference. If total is below base, reconciliation fails by definition. Total-only, admin flag. This is the shape a stale base takes after a price cut.
  • Fee rows. Already split out of the term grouping by #1587's termOf(r) === "signup_fee" branch. This build itemizes the fee's own tax the same way, using signup_fee_taxable.
  • Multi-currency. The header's currency phrase already suppresses itself when rows disagree. Unchanged.
  • DETAIL Miami's 9 offers. The renderer still reads only the first training offer. Pre-existing, out of scope, tracked in the money-model plan.
  • The stale GTA note. GTA's saved $185 to $565 pricing row stays inert - rendered facts outrank stored rows. Worth deleting in passing, but not a dependency.
