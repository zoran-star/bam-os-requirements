Put kids in the right class, by their actual age

Gate 1 · automation templating · 30 July 2026

Right now the sales agent works out which class a kid belongs in by reading the name of the calendar and looking for the words "Group 1" or "Group 2". That only works for BAM GTA, because GTA is the academy that named its classes that way. Every other academy gets nothing: San Jose's agent cannot offer a single trial time, and if a time reaches it another way it books whatever class it finds first. The fix is to stop reading names and start using the child's age as a number, against an age range the owner sets on each class.

What breaks, and exactly when

This is not on fire today, and I am not going to tell you it is. San Jose has zero sessions in the system right now, for a duller reason already on your launch list: sessions cannot be generated until Stripe is connected. So its agent offers no times today regardless of any of this.

It breaks the day San Jose's schedule is switched on, which is on the launch path. I ran the three real decision lines against San Jose's real classes (Beginner Tue 5-6pm, Elementary Tue 6-7pm, Pre-Season Wed + Fri 7-8pm). The moment those sessions exist:

AcademyTimes the agent offers a parentWhat happens on a booking
BAM GTA works right class
San Jose, once switched on zero. The parent is shown nothing at all books the first class in the list, whoever the child is

And GTA only works by coincidence. Its two sessions happen to be named Group 1 (Elementary) and Group 2 (High School), which is the exact text the matching looks for. It is not configured correctly, it is named correctly. All 86 of its sessions are missing the field that would say which class they belong to.

The same mistake, failing two opposite ways. Showing times fails shut (nothing appears). Booking fails open (it books anyway). That is why nobody has noticed: the half that goes wrong quietly is the half that writes to the database.

The part I want you to look at hardest

A 9-year-old beginner in San Jose can be put in the Elementary class, and every single step behaves correctly. Beginner runs 5pm, Elementary runs 6pm. Nothing anywhere filters the times a parent is offered by the child's age, so 6pm is on the list. The parent picks it. The system books Elementary, accurately, at 6pm, exactly as asked. Nothing is broken and the child is in the wrong class.

Which means fixing the booking step alone would fix nothing. The age has to decide which times get shown, not just which class gets written at the end. I am flagging this because the shorter version of this build looks finished and is not.

The clearest picture of the whole problem

Your staff "who is coming today" panel shows each kid's age group. For San Jose it would show the day of the week. It works out the age group by reading whatever is in brackets in the class name. Somebody once renamed GTA's classes by hand so that the brackets hold the age group. But when the system generates classes by itself, which is what every new academy gets, it puts the days in the brackets.

Class nameAge group your staff sees
Group 1 (Elementary)  GTA, renamed by handElementary
Free Trial - Beginner (Tue)Tue
Free Trial - Elementary (Tue)Tue
Free Trial - Pre-Season Academy (Wed, Fri)Wed, Fri

This is the whole build in one table. Nothing here is a typo or a bad regex. The class never carries which class it is, so seven different places each guess it from a piece of text, and they only agree for the one academy whose text was hand-tuned to make them agree. That is why a smarter guesser cannot fix it and the class has to be carried properly.

The one new thing an owner types

Each class already asks for an age. Today it is a free text box, so owners type U10 or Grades 5-8. A computer cannot route on that, and a grade means different ages in Ontario than in California, so we cannot safely convert it for them.

How you will know it is really finished

There is already a machine that answers this, so it is not my opinion. A check runs over every shared default hunting for one academy's details leaking into everybody's. It currently prints one known exception it is knowingly letting through: GTA's age bands. Done means that check reports zero deferred entries, with none of the seven copies parked on the exception list to buy a green result. It cannot be gamed, because the exception list prints on every run, including a passing one.

What actually changes

  • One resolver, api/agent/_class-routing.js, answers "which classes fit this age" and is the only thing allowed to answer it. Used by the agent, the free-trial website page, and DETAIL Miami's endpoint.
  • Two numbers per class (age_min, age_max) added to the offer's Schedule section in client-portal.html, alongside the existing free-text age which stays for display.
  • Carry the class onto the slot. schedule_slots.source_offer_class_key already exists and is indexed, and generate-slots.ts:199 already copies it template to slot. It is NULL everywhere because of two breaks in series, not one: _offer-schedule.js never puts it in the payload, and templates.ts:93-147 would not read it if it did. Both ends need fixing or the pipe stays dry.
  • Delete the name matching. groupOf() and both call sites in booking.js:142 and :223, plus the identical copies in leads.js:580 and miami-book.js:165.
  • Remove the four places that repeat GTA's age numbers: prompt-structure.js:628 (the booking_group body) and the three tool schemas at agent-approvals.js:133, :135, :151.
  • Remove the four places that depend on GTA's class NAMING, which carry no numbers and are the reason a smarter parser cannot help: booking.js:102-106 groupOf() plus its two call sites at :143 and :222, calendars-v15.js:184 groupFromSlot(), and the inline /group\s*\d+/i at leads.js:580 and miami-book.js:168.
  • Line numbers re-derived against this branch after PR #1656 merged, which moved most of them. One site I previously counted is already gone: the program section's "Adult classes: Group 2 (older group) only" was deleted by that PR and now survives only in a comment explaining its own removal. Counting it was the exact false reading this project warns about, and it is corrected here rather than quietly dropped.
  • Read the age as a number. athlete_age arrives as free text; unparseable means the agent asks, never guesses.

What must NOT change

  • GTA's rendered messages, byte for byte, except the class name replacing "Group 1". Locked by _gta-message-lock and _gta-step-lock.
  • {{appointment.entry_note}} and the venue resolution chain. Two suites depend on it and its fixture was corrected today.
  • No per-academy branch anywhere. Age ranges are runtime facts on the class.

How a tester proves it

  • A committed suite on plain node, no network, no database, with a negative control that must print NEGATIVE CONTROL PASSED.
  • Cases: age 9 with San Jose's three classes returns Beginner only; age 30 returns nothing and marks unqualified; a 9-year-old of unknown skill returns two and triggers exactly one question; GTA's two classes still route 9-13 and 14+ identically to today.
  • The finish condition above: the shared-default identity gate prints zero deferred entries.
