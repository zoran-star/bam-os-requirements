The long pole is Google, not us

The handoff doc flags it: the Business Profile API requires our Google Cloud project to be approved by Google, an application with a review process measured in days to weeks. Nothing per-academy can sync until that clears. Two things gate a connection, and only one of them is code:

  • Approval: Business Profile API access for the BAM Cloud project. Zoran-side console task. Start it first; everything else waits on it.
  • Ownership: each academy's Google Business Profile must be manageable by an account we can OAuth as, either the owner's Google account or BAM added as a manager on the profile.
San Jose cannot be connected, and would not help if it were. San Jose has not launched (site unpublished, per the launch-blockers note), so it has no review history. Even with Build 5 shipped and OAuth complete, a connected academy with zero reviews renders nothing under the recommended predicate. That is the guardrail behaving correctly, not a failure. GTA is the only academy with plausible review inventory today, and its shortlink destination still needs eyes on it to confirm the actual rating and review count.

The predicate

Recommended: a surface may render testimonial or review content only when the academy has a live Google Business Profile connection and at least one synced, displayable review (4 star or better). One shared helper, keyed on per-academy runtime state. Never a per-academy code branch.
Open question for Zoran: is the star threshold configurable per academy, or fixed at 4+ for everyone?

Build 5 (bam-ghl-agent/docs/google-reviews-build-handoff.md) is what makes this evaluable: per-academy OAuth storing place id, account id and refresh token on the client row, synced google_reviews rows, plus a curation ruleset. Build 5 has not shipped, so today no flag in the system means "connected."

The interim: one carve-out, everything else waits

Neither a full empty-by-default sweep nor an interim boolean was taken. Zoran's call is tolerate the existing state, prevent the new one:

Build now - the forward-looking trap

Nurture email 3 quote-free variant. An academy approving its drip is a routine click that would newly switch on re-attributed GTA quotes. That is fresh exposure created by a normal action, so it gets closed before the next academy approves a drip.

Wait for Build 5 - the existing state

The "Google review" labels on GTA and Miami, and the shared agent link reaching San Jose and Miami, stay as they are. They are known and accepted until a real connection can replace them with that academy's own reviews.

The through-line: nothing new turns on without a connection; what is already on is tolerated until the connection exists to fix it properly. The interim-boolean option was rejected on principle, and that principle holds for Build 5: connected must stay a checked fact, never a box a person ticks.

Consequence to hold in view. Everything except nurture 3 now depends on Build 5, and Build 5 depends on a Google approval that has not been applied for. The convergence wave is the pressure: every academy cloned from GTA before Build 5 lands inherits the review-shaped cards, exactly as Miami did. If the wave starts moving before the approval clears, this decision is worth revisiting.

Guardrails on the guardrail

  • Sales systems are shared. One mechanism keyed on per-academy runtime state, never a per-academy fork.
  • Attributed content never auto-propagates between academies (standing rule #55). A review belongs to the academy that earned it.
  • Enforcement checks trace what reaches output and whether gates fail open or closed. Never grep for literals. Three false positives this week came from literal greps, and this trace corrected two scout claims by reading render code.
Build spec (expand)

Shared predicate helper

Single exported function, one implementation, consumed by agent prompt rendering, email template rendering, and site config generation. Input: client id. Output: { connected, reviews[], aggregate }. Unconnected returns { connected:false, reviews:[], aggregate:null }, and every consumer treats that as "render nothing", never "render defaults".

Consumer changes

  • Agent: add a social_proof fact-renderer (the deliberate exclusion at fact-render.js:496-509 is what makes the default leak). Renderer returns empty when unconnected.
  • Emails: quote-bearing templates gain a quote-free variant selected at render time by the predicate.
  • Sites: testimonial config generated from the predicate. Rating block renders only from a real aggregate; no literal ratingScore in any config. The Google review source label may only appear on a row that came from a synced review.

Regression check

For a fixture academy with no connection, assert that agent output, each email body, and generated site config contain zero testimonial content and zero rating claim. Assert on rendered output, not source.
