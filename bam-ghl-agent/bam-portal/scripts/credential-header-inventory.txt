# CREDENTIAL HEADER MANIFEST - the RAW auth-header sites this scan can SEE.
#
# Format: "<rawSiteCount> <path>", plus optional "#drop <path> <who/why>" notes.
# Generated and checked by scripts/credential-header-scan.mjs; enforced by
# api/_credential-leak.test.mjs. NOTE: the portal CI job that runs it is
# ADVISORY, not a required check - a failure here shows a red X on the PR, it
# does not block a merge by itself.
#
# A RAW site is a line that builds a credential-bearing header (Authorization /
# apikey / x-api-key / Private-Token / Proxy-Authorization) from a credential
# that did NOT come through api/_header-safe-credential.js. Such a credential
# reaches fetch unchecked, and if it carries a line break INSIDE the finished
# header value, undici throws a TypeError QUOTING THE WHOLE VALUE with no
# .status - which any route doing `e.status || 500` + `e.message` hands straight
# back to the caller. That has shipped once, from the staff panel, with a live
# Stripe key.
#
# ── WHAT IS ACTUALLY ENFORCED ────────────────────────────────────────────────
# The scan matches ACROSS LINES and case-insensitively, and it understands:
#   object-literal keys, including a value wrapped onto later lines
#   property assignment          h.Authorization = v
#   computed-string assignment   h["Authorization"] = v
#   Headers.set / Headers.append with a string header name
#   new Headers([["Authorization", v]]) entry pairs
#   Object.assign(h, { Authorization: v })
#   credentials from process.env, INCLUDING the destructured
#     `const { SUPABASE_SERVICE_KEY } = process.env` form
#   credentials via the house env helpers - requireEnv("SUPABASE_SERVICE_ROLE_KEY"),
#     firstEnv(...), envPresent(...) - matched on the ARGUMENT name. Without this
#     the files that followed the codebase's own style were the ones outside the
#     bound: api/parent/_supabase.ts, the parent app's whole Supabase layer,
#     reported ZERO sites
#   a header value that is a CALL to a secret-returning helper (apikey: serviceKey())
#     or a property read off a config object (`Bearer ${c.apiKey}`)
#   credentials from ANY other source whose name says credential - a decrypted
#     row secret (decrypt*(...)), a stored per-academy token (client.x_token) -
#     because a DB credential in an auth header is the same hazard as an env one
#
# ── WHAT IS *NOT* ENFORCED, BY NAME ──────────────────────────────────────────
# These are invisible to the scan today. They are listed because a claim broader
# than the enforcement is the exact failure this whole change exists to punish:
#   1. COMPUTED HEADER NAMES from a variable - `const H = "Authorization";
#      { [H]: v }`. Needs constant propagation, which this scan does not do.
#   2. A credential whose NAME says nothing (`const a = row.b; { Authorization:
#      `Bearer ${a}` }`). Name-based detection cannot see it.
#   3. Header names assembled at runtime ("Auth" + "orization"), and template-
#      literal header keys.
#   3b. A CALLER-SUPPLIED token in an Authorization header whose variable is
#      named only `token` - e.g. api/parent/_supabase.ts:88. It is a real header
#      and a break in it still throws, but it carries the caller's OWN credential
#      rather than a server secret, and matching bare `token` would flood this
#      list. Named here rather than silently skipped.
#   4. Anything outside api/** - src/, scripts/ and the edge functions are not
#      scanned at all.
#   5. WHETHER A RAW SITE ACTUALLY REACHES A RESPONSE BODY. There is no sink
#      analysis; every raw site is treated as a hazard. That over-reports, which
#      is the right direction for a leak gate but means these counts are a
#      HAZARD INVENTORY, not a list of proven leaks.
# So: the counts below are a FLOOR, never a ceiling.
#
# ── WHAT THIS FILE IS ────────────────────────────────────────────────────────
# A COUNTED BASELINE of the population that existed on 2026-08-04, not a
# per-file audit and not an approval. Every line is a known hazard nobody has
# argued for. The standing reason is the same for all of them: this is the
# portal's long-standing Supabase/service-key access pattern, ~200 files deep,
# and converting it wholesale is a separate change from closing the leaks that
# were actually reachable. Recording the count is what stops it growing silently
# while that work is scheduled.
#
# ── WHAT IT IS FOR: FAIL-CLOSED ON ADDITION, AND ON QUIET SUBTRACTION ────────
# A new raw site in a listed file, or any raw site in an unlisted file, fails.
# A "#drop <path> <reason>" line may only vouch for a file that HAS a manifest
# line or a currently-visible site - an orphan witness is standing permission for
# a hazard added in a later PR, so it fails.
# A count that goes DOWN also fails unless the file now shows GUARDED sites or
# carries a "#drop <path> <reason>" line: a site can leave this scan by being
# fixed OR by being reformatted/extracted out of view with the credential still
# reaching fetch, and the two look identical from here. The gate must never
# print "lower the number" as the remedy for the second.
#
# HOW TO GET OFF THIS LIST. Route the credential through
# assertHeaderSafeCredential() + safeFetch() from api/_header-safe-credential.js,
# hoisting it to a local first (a guard called inside the header literal still
# reads as raw, on purpose - it keeps the value and its check in one place).
# Then lower the count, or delete the line at zero, IN THE SAME CHANGE.
#
# Zero raw sites, deliberately absent from this list: api/health.js,
# api/stripe/overview.js, api/commissions.js, api/website/checkout.js,
# api/website/camp-checkout.js, api/website/ch3-checkout.js, api/asana/tasks.js,
# api/notion/query.js.
